Complete Guide to Geographic Data Conversion

Master GeoJSON, KML/KMZ, ESRI Shapefile, and spatial CSV—how each format stores geometry, when to use which interchange path, and how to convert without losing precision or attributes.

~22 min read Updated Aug 3, 2026 abcGEO Editorial

Key takeaways

Quick summary

  • GeoJSON is the default for web maps (Leaflet, MapBox, MapLibre)—coordinates are always [longitude, latitude].
  • KML/KMZ remains the interchange format for Google Earth and many visualization pipelines; KMZ is zipped KML plus assets.
  • Shapefiles are a multi-file package (.shp, .dbf, .shx, plus projection). Missing siblings break the dataset.
  • Spatial CSV works for points and WKT geometries when headers, encoding (UTF-8), and CRS are explicit.
  • Most conversion failures come from CRS mismatches, precision truncation, encoding, or invalid multi-part geometries—not from the converter itself.

Introduction to spatial file formats

Answer-first

Geographic data conversion is the process of translating geometry and attributes between formats so GIS desktops, APIs, databases, and web maps can share the same features without loss of meaning.

Modern spatial workflows rarely live inside a single tool. A city planning team may maintain parcels in an enterprise geodatabase, publish open data as GeoJSON, hand field crews a KML for Google Earth, and feed analysts a CSV of sensor points. Each hop is a conversion. When conversion is sloppy—wrong axis order, truncated coordinates, dropped attributes, or an assumed CRS—maps look “almost right” until a boundary fails a topology check or a marker lands in the ocean.

Conversion matters because interoperability is the product. Web mapping libraries speak JSON. Desktop GIS still leans on Shapefile and geodatabase exports. Visualization and collaboration tools often expect KML. Spreadsheet-first teams deliver latitude/longitude columns. Bridging those worlds cleanly is what lets you ship reliable maps, reproducible analysis, and APIs that other systems can trust.

Three families of spatial data you will convert

Vector formats Discrete geometries (points, lines, polygons) with attributes—GeoJSON, Shapefile, many GIS exports.
Tabular spatial data Rows in CSV/TSV where location lives in columns (lat/lon) or a WKT geometry field.
XML-based spatial formats Hierarchical markup such as KML (and GML in OGC stacks) with styles, folders, and media references.
Binary / package formats Multi-file or compressed packages—Shapefile sidecars, KMZ archives—that must travel together.

This pillar focuses on the four interchange formats you will convert most often in GIS and web mapping: GeoJSON, KML/KMZ, ESRI Shapefile, and spatial CSV. After the format deep-dives, we cover conversion pitfalls and point you to live tools on abcGEO so you can validate workflows hands-on.

GeoJSON: the web-native spatial format

Answer-first

GeoJSON is a JSON encoding of geographic features (RFC 7946). Coordinates are [longitude, latitude] (and optional elevation) in WGS84 unless otherwise documented.

GeoJSON won the web because it is readable, compressible, and trivial to parse in JavaScript. Leaflet, Mapbox GL JS, MapLibre, OpenLayers, and most modern mapping APIs accept FeatureCollections directly. That makes GeoJSON the preferred interchange format when your destination is a browser, a Node service, or a JSON-first database.

Structure

A typical payload is a FeatureCollection containing Feature objects. Each feature has a geometry and a properties object for attributes. Geometry types include Point, MultiPoint, LineString, MultiLineString, Polygon, MultiPolygon, and GeometryCollection. 

{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "properties": { "name": "City Hall", "id": 42 },
      "geometry": {
        "type": "Point",
        "coordinates": [-122.4194, 37.7749]
      }
    }
  ]
}

Coordinate order: longitude, then latitude

This is the most common source of “why is my map empty?” bugs. GeoJSON uses longitude first (x, then y)—the opposite of the everyday “lat, lon” speech order and of many CSV conventions. [-122.4194, 37.7749] is San Francisco; swap the pair and you plot a point near Antarctica’s longitude band. Always verify axis order when converting from CSV, KML, or projected Shapefiles.

Use cases and web integration

  • Leaflet / MapLibre / Mapbox: load FeatureCollections as vector layers; style from properties.
  • APIs and microservices: return GeoJSON from REST or GraphQL endpoints without a binary GIS stack.
  • Static open data: publish downloadable .geojson files that humans and machines can inspect.
  • Validation pipelines: lint geometries (ring orientation, closed polygons) before they hit production maps.

Pros

  • Native to JavaScript and web maps
  • Human-readable and easy to version in git (for small files)
  • Clear geometry type system
  • RFC 7946 standardizes WGS84 lon/lat

Cons

  • Verbose for very large datasets
  • No built-in topology or CRS negotiation beyond WGS84
  • Attribute types are loosely typed JSON
  • Not ideal for multi-gigabyte national datasets

KML / KMZ: Keyhole Markup Language

Answer-first

KML is an XML language for geographic visualization (originally Keyhole, now an OGC standard). KMZ is a ZIP package of a KML file plus optional images and overlays.

KML grew up inside Google Earth. It remains the practical interchange format whenever stakeholders need fly-to placemarks, styled paths, network links, or ground overlays rather than a pure GIS attribute table. Many tourism, journalism, and field-operations workflows still export KML because Earth and Maps open it with almost no friction.

History and role today

Keyhole Markup Language was developed by Keyhole, Inc., acquired by Google in 2004. Google submitted KML to the Open Geospatial Consortium; it is now an OGC standard. Despite competition from GeoJSON on the web, KML still dominates “open this in Earth” collaboration and some CAD/visualization handoffs. KMZ exists because KML often references local images or models—zipping keeps the package portable.

XML structure (essentials)

A KML document is rooted at <kml> with a <Document> or <Folder> hierarchy. Features appear as <Placemark> elements containing a name, optional description, style references, and a geometry such as <Point>, <LineString>, or <Polygon>. Coordinates inside KML are also longitude, latitude[, altitude], space-separated. 

<?xml version="1.0" encoding="UTF-8"?>
<kml xmlns="http://www.opengis.net/kml/2.2">
  <Document>
    <Placemark>
      <name>City Hall</name>
      <Point>
        <coordinates>-122.4194,37.7749,0</coordinates>
      </Point>
    </Placemark>
  </Document>
</kml>

Google Earth integration

  • Double-click or import KML/KMZ into Google Earth for immediate 3D visualization.
  • Use folders and network links for large or frequently updated layers.
  • Preserve styles (Style, StyleMap) when round-tripping if visual presentation matters.
  • Expect richer presentation metadata than GeoJSON typically carries—and plan attribute mapping carefully when converting out of KML.

Pros

  • Excellent Earth / Maps interoperability
  • Styles, folders, and media in one model
  • KMZ packages travel as a single file
  • OGC-standardized lineage

Cons

  • XML is heavier than GeoJSON for web apps
  • Attribute models vary by exporter
  • Complex KML (tours, network links) does not map 1:1 to FeatureCollections
  • Parsing requires an XML toolchain

ESRI Shapefile: legacy standard, multi-file reality

Answer-first

A Shapefile is not one file—it is a mandatory trio (.shp, .shx, .dbf) plus optional sidecars like .prj. Lose any required sibling and the dataset is incomplete.

The ESRI Shapefile format dates to the early 1990s and remains ubiquitous in government open data portals, consulting deliverables, and desktop GIS. It is a de facto legacy standard: widely supported, well documented, and constrained by design choices that modern formats improve upon (field name length, lack of null geometry handling richness, multi-file packaging).

Multi-file structure quirks

Extension Role Required?
.shp Geometry (shapes) Yes
.shx Shape index for fast seeking Yes
.dbf Attribute table (dBASE) Yes
.prj Coordinate reference system (WKT text) Strongly recommended
.cpg Character encoding for the DBF Recommended for non-ASCII
.sbn / .sbx Spatial index (optional) No

Emailing only the .shp is a classic failure mode. Always zip the full set, or convert to a single-file format (GeoJSON, GeoPackage) before sharing with non-GIS audiences. Field names in the DBF are limited (historically 10 characters), which forces ugly abbreviations and collisions when converting from richer schemas.

Coordinate system dependency

Geometry in the .shp is stored in whatever projected or geographic coordinates the author used. The .prj file tells software how to interpret those numbers. Without a .prj, converters may assume WGS84—or refuse to guess. That is how a perfectly valid county polygon set ends up offset by hundreds of meters (or degrees) after “successful” conversion. Always confirm the source CRS, reproject deliberately (for example to EPSG:4326 for web maps), then export.

Pros

  • Universal GIS support
  • Fast for many desktop workflows
  • Familiar to agencies and contractors
  • Stable, well-known binary layout

Cons

  • Multi-file packaging is fragile
  • Attribute and Unicode limitations
  • No mixed geometry types in one layer
  • Projection easy to lose without .prj

Spatial CSV and delimited text

Answer-first

Spatial CSV stores locations as latitude/longitude columns or as a WKT geometry attribute. Success depends on clear headers, UTF-8 encoding, and an explicit CRS assumption.

Spreadsheets remain the most common “GIS” for non-specialists. A CSV of store locations, incident reports, or sensor readings can become a map layer in minutes— if the location columns are unambiguous. Delimited text is also how many ETL jobs ferry points between databases and mapping tools.

Latitude / longitude point data

The simplest pattern is two numeric columns. Name them clearly—prefer longitude / latitude or lon / lat over vague x / y unless you document the CRS. Confirm decimal degrees versus projected meters. Include a header row; converters should not have to guess. 

id,name,longitude,latitude
1,City Hall,-122.4194,37.7749
2,Ferry Building,-122.3933,37.7955

WKT geometry attributes

When you need lines or polygons in a table, store Well-Known Text in a dedicated column (often named wkt or geometry). WKT is a textual encoding such as POINT (-122.4194 37.7749) or POLYGON ((...)). Many databases and GIS tools import WKT cleanly; just ensure the axis order matches your CRS convention (for geographic WGS84, longitude then latitude inside WKT is typical).

Header and encoding requirements

  • Headers: first row must name columns; avoid duplicate names and special characters that break parsers.
  • UTF-8: save as UTF-8 (with or without BOM, consistently). Latin-1 DBF exports often corrupt names when merged into CSV.
  • Delimiter: comma is default; if values contain commas, quote fields. Prefer TSV when free text is messy.
  • Nulls: empty cells vs NA—document the convention so converters do not invent zeros.
  • CRS: state it in a sidecar README or metadata column; do not assume every consumer knows your city’s local projection.

Pros

  • Universal and spreadsheet-friendly
  • Easy diffs and lightweight ETL
  • Great for point datasets
  • WKT extends beyond points

Cons

  • Ambiguous column naming is common
  • Weak typing and inconsistent nulls
  • Large polygons make huge text cells
  • No native topology or styles

Conversion workflow and common pitfalls

Answer-first

Reliable conversion is a checklist: confirm CRS, preserve precision, force UTF-8, validate geometries (especially multi-polygons), then smoke-test in the target map client.

Treat conversion as a pipeline, not a button. Source → inspect → reproject (if needed) → convert → validate → load in the destination. Skipping inspection is how “successful” exports still fail QA.

Recommended workflow

  1. Inventory the source: format, CRS, encoding, geometry types, attribute schema, and file completeness (especially Shapefile sidecars).
  2. Decide the target CRS: WGS84 / EPSG:4326 for most web maps; Web Mercator (EPSG:3857) only when tiles or meters-on-screen demand it.
  3. Convert with an explicit tool chain: abcGEO converters on tools.html#converters, GDAL/OGR, or QGIS—avoid mystery online converters for regulated data.
  4. Validate: feature count, bbox, sample attributes, ring closure, and a visual overlay against a known basemap.
  5. Document: record source CRS, conversion date, and any field renames so the next person does not reverse your longitude again.

Pitfalls that break maps

  • Precision loss Rounding coordinates to 4–5 decimal places may be fine for city-scale pins, but parcel boundaries and survey-grade lines need more. Binary formats and some CSV exports silently truncate. Prefer full double precision until you deliberately generalize for web delivery.
  • Coordinate transformation (WGS84 vs projected EPSG codes) Converting formats is not the same as reprojecting. If your Shapefile is EPSG:2227 (or another local projection) and you emit GeoJSON without transforming to EPSG:4326, web maps will misplace every vertex. Always reproject with a known library (PROJ/GDAL) and verify the .prj or metadata.
  • Character encoding (UTF-8) Shapefile DBF files frequently ship in legacy code pages. Without a matching .cpg (or an explicit encoding flag), city names and street attributes corrupt on conversion. Normalize to UTF-8 at the boundary into GeoJSON, KML, and CSV.
  • Multi-polygon and multi-part geometries Exporters disagree on whether islands belong in MultiPolygon, separate features, or nested rings. Invalid holes (wrong winding, unclosed rings, self-intersections) may pass a naive converter and fail in Mapbox GL, PostGIS, or topology checks. Validate with a geometry linter after conversion.
  • Axis order and altitude GeoJSON and KML expect lon/lat; some CSVs and APIs say lat/lon. Altitude/Z values may be ignored by 2D web maps or misread as part of 2D coordinates. Strip or isolate Z deliberately.
Practical rule: if the converted layer looks plausible at world scale but wrong at street scale, suspect CRS—not your basemap. If attributes look like cafÃ©, suspect encoding. If half the polygons vanish, suspect multi-part or invalid rings.
